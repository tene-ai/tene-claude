## 1. 배경 (Why)

### 1.1 해결하려는 문제

바이브 코딩은 두 지점에서 무너진다.

| # | 실패 지점 | 구체적 증상 |
|---|---|---|
| **P1** | **의도의 휘발** | 기획 의도가 대화 세션에만 존재한다. Claude Code는 매 세션 새 컨텍스트로 시작하므로, 다음 세션은 "왜 이렇게 만들었는지"를 모른다. 리팩터링이 의도를 조용히 파괴한다. |
| **P2** | **판정 기준(oracle)의 부재** | 유닛/E2E 테스트의 판정 기준은 전부 코드에서 유도된 것이다. 따라서 "코드가 기획과 다르게 구현된 경우"를 원리적으로 잡을 수 없다. UX 흐름·데이터 처리 흐름·화면 전이는 어떤 단일 파일에도 없다. |
| **P3** | **단편적 판단으로 인한 기술 부채** | LLM은 숲(전체 구조)과 나무(개별 심볼)를 복합적으로 조사하지 않고 눈앞의 파일만 보고 판단한다. 그 결과 중복 구현, 잘못된 계층 배치, 스파게티 코드가 누적된다. |
| **P4** | **작업 흐름의 비체계성** | 요구사항 → 계획 → 설계 → 구현 → 검증이 한 세션에 뭉개진다. 무엇이 끝났고 무엇이 남았는지 세션을 넘기면 알 수 없다. |
| **P5** | **비밀정보 유출** | API 키·토큰이 `.env` 평문으로 존재하고, AI 에이전트의 컨텍스트 윈도우에 그대로 들어간다. |

### 1.2 기존 해법의 한계

| 카테고리 | 대표 | 한계 |
|---|---|---|
| AI QA 도구 | Momentic, QA.tech, testRigor | 이미 만들어진 앱을 사후 테스트. **기획 대화에서 의도를 캡처하는 단계가 없다** |
| SDD 프레임워크 | Spec Kit, BMAD, OpenSpec, Kiro | 스펙은 잘 만들지만 **QA로 연결되지 않고**, 코드 변경 시 스펙이 낡았음을 알려주지 않는다 |
| 요구사항 관리 | Jama, Visure | 추적성은 성숙하나 **코드 구조와 연결되지 않고** AI 코딩 워크플로 밖에 있다 |
| 코드 그래프 | CodeGraph, GitNexus | 구조는 주지만 **의도도 QA도 없다** |

> 상세 분석: [00-rnd/04-intent-driven-qa-research.md §2](../00-rnd/04-intent-driven-qa-research.md)

### 1.3 우리가 가진 비대칭 자산

| 자산 | 내용 | PRD상 의미 |
|---|---|---|
| **누적된 방법론** | sprint 사이클 운영 경험, 문서 폴더 규약, 훅 기반 게이트 | P4의 검증된 절차 |
| **Understanding Layer + 6가지 질문** | LLM의 단편적 판단을 막는 검증된 사고 프레임 | P3의 직접 해결 수단 |
| **tene CLI** (선택적 연동) | XChaCha20-Poly1305 로컬 암호화 시크릿 관리. `tene run --` 주입 | P5의 완결된 해결 수단 |

### 1.4 독립성 제약 (가장 중요한 설계 전제)

> **tene 플러그인은 어떤 외부 제품에도 의존하지 않는다.**

| 대상 | 관계 |
|---|---|
| tene studio / tene MCP | ❌ 무관. 참조·의존 금지 (studio 내장 기능, 별도 제품) |
| bkit 등 타 워크플로 플러그인 | ❌ 무관. 병존만 보장 |
| tene CLI | ⚠️ **선택적 연동**. 설치되어 있으면 활용, 없으면 조용히 비활성화 |
| Claude Code 내장 기능 | ✅ 유일한 기반 |

따라서 코드 구조 파악(P2·P3의 수단)은 **플러그인이 스스로 해결해야 한다.** 이를 위해 3단 폴백 어댑터(LSP → 자체 인덱서 → 에이전트 조사)를 설계한다. 상세는 [아키텍처 §2](./02-plugin-architecture.md).

## 2. 제품 정의 (What)

### 2.1 한 문장

> **tene 은 기획 의도를 문서로 붙잡아 코드에 앵커링하고, 그 의도를 판정 기준 삼아 sprint 사이클마다 반복 검증하는 Claude Code 플러그인이다.**

### 2.2 제품 원칙 (Product Principles)

| # | 원칙 | 함의 |
|---|---|---|
| **PP1** | **의도는 문서에, 강제는 훅에** | CLAUDE.md는 권고일 뿐이다. 지켜져야 하는 것은 hook exit 2로 내린다 |
| **PP2** | **추측 금지, 출처 명시** | 구조에 대한 판단은 근거(`file:line`)와 출처 Tier를 반드시 동반한다. 모르면 모른다고 적는다 |
| **PP3** | **미측정을 통과로 뭉개지 않는다** | `insufficient`는 `pass`도 `fail`도 아닌 1급 판정이다 |
| **PP4** | **작성자가 자기 작업을 채점하지 않는다** | 검증은 별도 컨텍스트(서브에이전트/워크플로)에서 수행한다 |
| **PP5** | **컨텍스트는 유한 자원** | 문서 전량 로드 금지. 인덱스 + 경로 스코프 + JIT 조회 |
| **PP6** | **양식은 고정, 관점은 자유** | 필수 섹션은 항상 동일. 그 위에 자유 관점(`+@`)을 얹는 것은 허용 |
| **PP7** | **비밀정보는 절대 컨텍스트에 넣지 않는다** | `tene run --` 주입만 허용. `tene get`/`tene export` 금지 |

### 2.3 범위 밖 (Non-goals)

- ❌ 자체 테스트 러너 구현 — 프로젝트의 기존 러너(jest/vitest/pytest/go test/playwright)를 호출한다
- ❌ 완전한 콜그래프/타입 추론 엔진 구현 — LSP가 있으면 쓰고, 없으면 "단편적 판단을 막을 만큼"의 경량 인덱스로 충분하다
- ❌ 특정 언어/프레임워크 전용화 — 언어 중립. 인덱서가 지원하지 않는 언어에서도 절차는 유지되고 정밀도만 낮아진다
- ❌ 클라우드 서비스 의존 — 로컬 우선. 네트워크 없이도 핵심 사이클이 돌아야 한다
- ❌ 기존 PDCA 플러그인 대체 선언 — 병존 가능해야 한다 (상태 디렉토리 분리)

## 3. 사용자와 시나리오 (Who)

### 3.1 사용자 유형

| 유형 | 특성 | 핵심 니즈 |
|---|---|---|
| **U1 · 1인 개발자 / 바이브 코더** | 기획·개발·QA를 혼자 함. 세션을 자주 넘김 | 세션 간 맥락 유지, 빠뜨린 것 자동 발견 |
| **U2 · 소규모 팀 리드** | 여러 사람이 같은 저장소에서 AI로 작업 | 문서 양식 통일, 리뷰 가능한 산출물, 진행 상태 가시화 |
| **U3 · 외부 도입자** | 다른 프로젝트에 플러그인만 설치 | 프로젝트 무관 동작, 낮은 설정 부담, 안전한 기본값 |

### 3.2 대표 시나리오

**S1 · 새 기능을 sprint로 처리한다 (U1)**
```
/tene:sprint init checkout-retry
  → 대화형 인터뷰로 PRD 작성 (docs/sprints/checkout-retry/00-prd/)
/tene:sprint start checkout-retry
  → plan → design → do → check → qa → report 자동 진행 (Trust Level 범위 내)
  → 각 단계 산출물이 고정 양식으로 폴더에 쌓임
```

**S2 · 세션을 넘긴 뒤 이어서 작업한다 (U1)**
```
(새 세션 시작)
SessionStart 훅이 진행 중 sprint와 현재 phase, 미완 항목을 컨텍스트에 주입
"이어서 해줘" → 현재 phase부터 재개
```

**S3 · 구현이 기획과 다른지 검증한다 (U1/U2)**
```
/tene:loop-check checkout-retry
  → PRD/plan/design 문서의 수용 기준을 추출
  → Understanding Layer 4계층별 구현 현황 대조
  → 6가지 질문에 결정론적으로 답변
  → 불일치 항목을 개선 태스크로 생성, 100% 달성까지 반복
```

**S4 · UX 흐름과 데이터 흐름을 종합 테스트한다 (U1/U2)**
```
/tene:qa checkout-retry
  → 수용 기준을 UNIT / DATA / UX 3갈래로 분류
  → UNIT: 프로젝트 테스트 러너 실행
  → DATA: 코드 지능 어댑터 질의 + 실행 결과 대조로 데이터 흐름 검증
  → UX : Chrome MCP(또는 Playwright)로 화면 전이 시나리오 실행
  → 전이 커버리지 산출, 미측정은 미측정으로 보고
  → 게이트 미달 시 report 진입 차단
```

**S5 · 비밀정보를 안전하게 다룬다 (전체)**
```
사용자: "Stripe 키를 넣어서 개발서버 띄워줘"
  → tene-secrets 스킬 트리거
  → `tene run -- npm run dev` 로 안내. 평문은 컨텍스트에 절대 미진입
```

**S6 · 팀이 같은 양식으로 일한다 (U2)**
```
누가 작성해도 PRD/plan/design/analysis/qa/report가 같은 섹션 구조를 갖는다
→ 리뷰 비용 감소, 다음 sprint가 이전 sprint를 기계적으로 참조 가능
```

## 4. 기능 요구사항 (FR)

### FR-1 · Sprint 사이클 엔진

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-1.1 | 8단계 sprint 사이클을 제공한다: `prd → plan → design → do → check → qa → report → archive` | 각 단계 진입/이탈이 상태 파일에 기록되고 `/tene:sprint status`로 조회된다 |
| FR-1.2 | 단계 전이는 **선행 단계의 산출물이 존재하고 게이트를 통과했을 때만** 허용한다 | design 문서 없이 do 진입 시 거부되고 사유가 제시된다 |
| FR-1.3 | `loop-check` 단계는 PRD/plan/design 대비 구현 일치율을 산출하고, 목표(기본 100%) 미달 시 개선 작업을 반복한다 | 반복 상한(기본 3회)에 도달하면 정지하고 잔여 갭을 보고한다 |
| FR-1.4 | `qa` 단계는 UNIT/DATA/UX 3갈래 검증을 수행하고 게이트 판정을 내린다 | 게이트 결과가 `pass`/`fail`/`blocked` 중 하나로 기록되고, `fail`이면 report 진입이 차단된다 |
| FR-1.5 | 여러 sprint를 묶는 **sprint master plan**을 작성·관리한다 | master plan에서 sprint 목록·순서·의존·상태를 한 화면에서 본다 |
| FR-1.6 | sprint를 일시정지/재개/포크/아카이브할 수 있다 | 각 조작이 상태에 반영되고 이력이 남는다 |

### FR-2 · 문서 표준화

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-2.1 | prd / plan / design / analysis / qa / report 6종 문서의 **필수 섹션**을 정의하고 템플릿으로 제공한다 | 템플릿 없이 작성된 문서는 검증 스킬이 누락 섹션을 지적한다 |
| FR-2.2 | 필수 섹션 외 **자유 관점 섹션(`+@`)** 추가를 허용한다 | 자유 섹션이 있어도 검증이 통과한다 |
| FR-2.3 | 모든 문서는 YAML frontmatter로 기계 판독 가능한 메타데이터를 갖는다 | sprint id, phase, status, 갱신시각, 앵커가 파싱된다 |
| FR-2.4 | report 문서는 §5의 6개 필수 항목을 포함한다 | 6개 항목 중 하나라도 없으면 report 완료로 표시되지 않는다 |
| FR-2.5 | 문서는 sprint별 폴더 계층으로 관리한다 | `docs/sprints/<sprint-id>/{00-prd,01-plan,02-design,03-analysis,04-report}/` |

### FR-3 · Understanding Layer & 6가지 질문 (기술부채 방어)

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-3.1 | 모든 설계·구현·보고 산출물은 작업 대상을 **Understanding Layer 4계층**으로 분류한다 | Interface / Business Logic / Persistence / Infrastructure 각각에 대해 "해당 없음"을 포함해 명시된다 |
| FR-3.2 | 계층 분류는 **규칙 파일 기반으로 결정론적으로 수행**하고, 규칙에 매칭되지 않는 항목은 **미분류로 남긴다** | 추론으로 채운 계층은 `source: imports, confidence: medium` 등으로 등급 표기된다. 미분류를 억지로 채우지 않는다 |
| FR-3.3 | 변경된 처리 로직에 대해 **6가지 질문**에 답한다 | 6개 질문 각각에 근거(`file:line` 또는 질의 결과)와 출처 Tier가 붙는다 |
| FR-3.4 | 6가지 질문은 3단 폴백(LSP → 자체 인덱서 → 에이전트 조사)으로 답하고, **어느 Tier가 답했는지 항상 표기**한다 | `source: lsp｜indexed｜investigated` 가 문서에 남는다 |
| FR-3.5 | 계층 위반(예: Interface에서 DB 직접 접근)을 감지하면 경고한다 | 경고가 analysis 문서에 기록된다 |

### FR-4 · 의도 보존과 QA 연결

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-4.1 | PRD 작성 시 대화형 인터뷰로 기획 의도를 추출한다 | 목적·사용자 가치·**범위 밖**·되돌아오는 경로·실패 조건이 질문된다 |
| FR-4.2 | 의도는 **수용 기준(AC)** 으로 정규화되고, 각 AC는 검증 방식(UNIT/DATA/UX)이 태깅된다 | AC마다 고유 ID(`AC-1`…)와 방식 태그를 갖는다 |
| FR-4.3 | 각 AC는 코드 심볼/엔드포인트/화면에 **앵커링**된다 | 앵커가 문서 frontmatter와 상태 인덱스에 기록된다 |
| FR-4.4 | 코드 변경 시 영향받는 AC를 자동으로 `stale`로 표시한다 | 편집 직후 해당 AC가 재검증 대상으로 전환된다 |
| FR-4.5 | UX 흐름 검증은 **설계 문서에 정의된 화면 전이 엣지**에 대한 커버리지를 산출한다 | `측정 엣지 / 전체 엣지` 비율이 qa 문서에 기록된다 |
| FR-4.6 | 데이터 처리 흐름 검증은 코드 지능 어댑터 질의(변경 지점·영속화 호출·계약)와 실행 결과 대조로 수행한다 | UI만으로 잡히지 않는 영속화 누락이 검출된다 |
| FR-4.7 | QA 판정은 **증거 수집과 판정을 분리**하고, 통과 판정에 대해 적대적 재검증을 수행한다 | 판정마다 증거 경로가 남는다 |

### FR-5 · 상태·메모리 관리

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-5.1 | sprint 사이클과 master plan의 진행 상태를 파일로 기록한다 | 새 세션에서 상태 파일만으로 현재 위치를 복원할 수 있다 |
| FR-5.2 | 세션 시작 시 진행 중 sprint·phase·미완 항목을 컨텍스트에 주입한다 | 사용자가 별도 설명 없이 "이어서"라고 말할 수 있다 |
| FR-5.3 | 장기 학습은 Claude Code auto memory에 축적한다 | 프로젝트 관례·함정이 세션을 넘어 유지된다 |
| FR-5.4 | 상태 파일의 **비대화를 방지하는 정리(clear/compact) 기능**을 제공한다 | 이력 상한 초과분이 아카이브로 이동하고 활성 파일은 상한 이하로 유지된다 |
| FR-5.5 | 상태 저장 위치는 tene CLI의 `.tene/`와 **충돌하지 않는다** | 별도 디렉토리를 사용하고, `.tene/`를 절대 읽거나 쓰지 않는다 |

### FR-6 · 호출과 트리거

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-6.1 | 모든 주요 기능은 `/tene:<name>` 형태로 직접 호출된다 | `/help` 커스텀 커맨드 탭에 나타난다 |
| FR-6.2 | 직접 호출하지 않아도 자연어 요청의 키워드로 적절한 스킬이 트리거된다 | "이 기능 QA 해줘" → qa 스킬이 활성화된다 |
| FR-6.3 | 부작용이 큰 작업(archive, 전체 재검증 등)은 **모델 자동 호출을 금지**한다 | `disable-model-invocation: true` |
| FR-6.4 | 트리거는 다국어(최소 한국어/영어)를 지원한다 | 한국어 요청에서도 정상 트리거된다 |
| FR-6.5 | 오탐 시 사용자가 트리거를 끌 수 있다 | 설정으로 자동 트리거 비활성화가 가능하다 |

### FR-7 · tene CLI 시크릿 연동

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-7.1 | 비밀정보 관련 요청 시 tene CLI 사용법을 기억하고 안내한다 | 스킬이 자동 트리거되어 올바른 명령을 제시한다 |
| FR-7.2 | 평문 노출 명령(`tene get`, 비암호화 `tene export`, `.tene/` 읽기)을 **훅으로 차단**한다 | 시도 시 거부되고 대안이 제시된다 |
| FR-7.3 | 실행 명령은 `tene run --` 주입 형태로 제안한다 | `npm run dev` 대신 `tene run -- npm run dev` |
| FR-7.4 | `.env` 평문 파일 생성/커밋을 감지해 경고한다 | 경고와 마이그레이션 절차가 제시된다 |
| FR-7.5 | tene 미설치 프로젝트에서는 기능이 조용히 비활성화된다 | 오류 없이 넘어간다 |

## 5. report 문서 필수 항목 (사용자 지정)

report는 **사용자와 AI가 함께 회고**하기 위한 문서다. 다음 6개 항목이 필수다.

| # | 항목 | 목적 | 자동 채움 가능성 |
|---|---|---|---|
| **R1** | 이전 sprint 구현 내용과 **어떻게 기능이 이어지는지** | 연속성 파악, 고립된 기능 방지 | 이전 sprint report + 참조·호출 질의로 초안 생성 |
| **R2** | **어떤 파일을 생성·수정**했고, 어떤 기능을 어떻게 구현했는지 | 변경 범위 파악 | git diff + 계층 판정으로 자동 생성 |
| **R3** | 개발한 처리 로직이 **어떤 기획 의도를 충족**시키기 위한 것인지 | 의도↔구현 연결 유지 | AC 앵커 역참조로 자동 생성 |
| **R4** | **Understanding Layer 4계층** 기준으로 어떤 작업을 했는지 | 계층 균형·위반 확인 | 계층 규칙 파일로 자동 분류 (미분류는 미분류로) |
| **R5** | 처리 로직에 대한 **6가지 질문** 답변 | 숲과 나무의 복합 파악, 기술부채 방어 | 코드 지능 어댑터 3단 폴백으로 자동 수집, 출처 Tier 표기 |
| **R6** | **사용자가 정해야 하는 정책**과 **이월한 작업**, 그리고 이번에 하지 않은 이유 | 의사결정 대기 항목 명시화, 무언의 누락 방지 | 대화 중 미결 항목 + 게이트 미달 항목에서 수집 |

> **R4·R5가 이 제품의 방어 장치다.** LLM이 눈앞의 파일만 보고 판단해 기술부채와 스파게티 코드를 만드는 것을 막기 위해, 매 sprint마다 전체 구조(4계층)와 개별 심볼(6질문)을 **동시에** 강제 확인시킨다.

## 9. 마일스톤

## 부록 A · 용어

| 용어 | 정의 |
|---|---|
| **Sprint** | prd~archive 8단계를 한 번 도는 작업 단위. 하나 이상의 기능을 포함 |
| **Sprint Master Plan** | 여러 sprint의 순서·의존·상태를 묶는 상위 계획 |
| **AC (Acceptance Criterion)** | 기획 의도를 판정 가능한 문장으로 정규화한 것. 검증 방식이 태깅됨 |
| **Anchor** | AC와 코드 심볼/엔드포인트/화면을 잇는 참조 |
| **Understanding Layer** | Interface / Business Logic / Persistence / Infrastructure 4계층 |
| **6가지 질문** | 정의명·정의위치·참조위치·호출위치·입력형태·출력형태 |
| **Gate** | phase 전이를 허용/차단하는 판정 지점 |
| **Trust Level** | 사용자 확인 없이 자동 진행할 수 있는 범위 (L0~L4) |
| **stale** | 코드 변경으로 재검증이 필요해진 AC의 상태 |
| **insufficient** | 검증을 시도하지 못한 상태. pass도 fail도 아님 |
