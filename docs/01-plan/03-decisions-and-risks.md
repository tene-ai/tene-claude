## 1. 확정 결정 (DEC)

| ID | 결정 | 근거 | 재검토 조건 |
|---|---|---|---|
| **DEC-01** | 코어를 **공유하지 않는다.** Claude Code 네이티브 + 경량 Node 스크립트 | `tene-workflow` 는 Codex 에 Dynamic Workflow 가 없어서 만드는 대체물. Claude 쪽은 런타임이 이미 제공 | Claude Code 가 워크플로를 제거할 때 |
| **DEC-02** | 스크립트는 **순수 Node, 외부 의존 0** | 설치 부담 제거. `npm install` 없이 동작 | 성능이 병목이 될 때 |
| **DEC-03** | 상태는 **파일(JSON/NDJSON)**, DB 아님 | git diff·리뷰·수동 편집 가능. 플러그인을 지워도 읽힌다 | 그래프 규모가 파일로 감당 안 될 때 |
| **DEC-04** | **Markdown 은 사람, JSON 은 기계** | 편집성과 결정성 분리. 문서가 정본, 상태는 파생 | 없음 |
| **DEC-05** | 게이트는 **blocking AC 이진 판정** | 백분율은 분모 조작 가능, 평균은 치명 결함 희석 | 없음 |
| **DEC-06** | 기본 Profile `standard` | 규율과 도입성의 균형 | Dogfooding 마찰 관측 후 |
| **DEC-07** | 계층 분류는 **규칙 파일 우선**, 미매칭은 미분류 | 결정론·재현성·팀 공유·사용자 교정 | 없음 |
| **DEC-08** | 훅은 **보조 안전망**, 코어 정확성이 훅에 의존하지 않음 | 훅 가용성이 버전·신뢰 설정에 따라 다름 | 없음 |
| **DEC-09** | 수집자와 판정자 **분리** | 자기 작업 채점 편향 제거 | 없음 |
| **DEC-10** | `tene-guard` 만 **fail-closed**, 나머지 fail-open | 보안은 막는 쪽이 안전, 워크플로는 여는 쪽이 안전 | 없음 |
| **DEC-11** | 상태 디렉토리 `.tene-claude/` (Codex 와 분리) | 스키마가 다른데 같은 이름을 쓰면 호환을 오해시킨다 | 스키마가 실제로 통일될 때 |
| **DEC-12** | `docs/sprints/` 규약은 **tene-codex 와 통일** | 문서가 정본이므로 문서만 같으면 상호 인계 가능 | 없음 |
| **DEC-13** | Dynamic Workflow 는 **팬아웃 전용** (임계 이상일 때만) | 워크플로는 비싸고 사용자 입력을 못 받는다 | 비용 구조 변화 시 |
| **DEC-14** | Intent 와 AC 를 **분리** (tene-codex 차용) | 하나의 의도가 여러 기준을 낳는다. 출처 추적 가능 | 없음 |
| **DEC-15** | 라이선스 **Apache-2.0** | tene-codex 와 동일. 특허 조항 포함 | 없음 |

## 2. 대안 검토 기록

### 2.1 `tene-workflow` Go 코어 공유 — 기각

| 장점 | 단점 |
|---|---|
| 두 호스트가 같은 상태를 공유 | **아직 존재하지 않음** → 착수 불가 |
| 로직 중복 없음 | 릴리즈 커플링 |
| 그래프 엔진이 강력 | 플랫폼별 바이너리 배포·checksum 부담 |
| | Claude Code 네이티브 기능과 역할 중복 |

**기각 사유**: Claude Code 는 Dynamic Workflow·Task Management·Hooks 로 코어가 하려는 일의 대부분을 이미 한다. 없는 것을 만든 도구를 있는 쪽이 가져다 쓰는 것은 역방향이다.

**대신 채택**: 개념·스키마·문서 규약은 차용, 런타임은 분리.

### 2.2 TypeScript + 빌드 — 기각

빌드 산출물이 생기면 플러그인 배포 시 소스/산출물 동기화 문제가 생긴다. 플러그인은 소스가 곧 배포물이어야 한다.

**대신**: 순수 JS(ESM) + JSDoc 타입 주석. IDE 타입 힌트는 유지된다.

### 2.3 SQLite 상태 저장 — 기각

트랜잭션과 쿼리는 좋지만 git diff·리뷰·수동 편집이 불가능해진다. 플러그인을 제거해도 산출물이 읽혀야 한다는 원칙(NFR-7)에 어긋난다.

**대신**: JSON + NDJSON. 대형 인덱스가 병목이 되면 그때 derived cache 로만 도입.

### 2.4 tree-sitter / ripgrep 의존 — 기각

정확도는 오르지만 외부 설치를 요구한다. 도입 장벽이 커진다.

**대신**: 순수 Node 정규식 인덱서 + `rg` 가 PATH 에 있으면 사용(선택적 가속). LSP 가 있으면 Tier 1 로 승격.

### 2.5 자체 MCP 서버 제공 — 기각

MCP 서버는 상시 컨텍스트 비용(도구 이름)과 설치 부담을 만든다. 훅과 `bin/` 스크립트로 같은 일을 할 수 있다.

### 2.6 모든 작업에 strict 사이클 강제 — 기각

품질은 오르지만 사소한 작업의 도입성을 해친다. 오탈자 수정에 PRD 를 요구할 수 없다.

**대신**: Profile 로 규율 강도를 조절하되, **어느 Profile 에서도 단계를 건너뛰지는 않는다**(필수 섹션 수만 줄어든다).

### 2.7 이벤트 해시 체인 — MVP 보류

tene-codex 는 `previous_hash`/`hash` 체인으로 저널 무결성을 보장한다. 감사 요구가 명확할 때 가치가 있으나, 단일 사용자 시나리오에서는 과잉이다.

**MVP**: 단순 append NDJSON. 감사 요구가 생기면 스키마 버전 올려 추가.

## 3. MVP 에서 의도적으로 하지 않는 것 (YAGNI)

| 항목 | 하지 않는 이유 | 나중에 필요해질 신호 |
|---|---|---|
| 다중 홉 영향 분석 (`impact` 순회) | 6질문은 1홉으로 충분. 다중 홉은 정확도 대비 비용이 큼 | 대규모 리팩터링 요구가 반복될 때 |
| 통합 그래프 DB (노드/엣지 저장소) | 역인덱스 2개로 필요를 충족 | 관계 질의가 복잡해질 때 |
| 이벤트 해시 체인 | 단일 사용자에 과잉 | 팀 감사 요구 |
| `revision` uint64 + expected-revision | `updatedAt` 낙관적 잠금으로 충분 | 동시 세션 충돌이 실제 발생할 때 |
| 팀 협업 동시성 제어 | 낙관적 잠금 + 경고로 시작 | 팀 사용 보고 |
| 웹 대시보드 / 원격 UI | Claude Code 안에서 완결 | — |
| sprint 간 의존 자동 추론 | 잘못된 추론의 비용 > 수동 선언 비용 | — |
| 다국어 8종 지원 | ko/en 으로 시작 | 사용자 요청 |
| 자체 테스트 러너 | 프로젝트 러너를 호출 | — |
| 클라우드 동기화 | 로컬 우선 | — |
| 요구사항 변경 diff 시각화 | git diff 로 충분 | — |
| 5종 초과 언어 팩 | ts/js/py/go/java 로 시작, 나머지는 Tier 3 | 사용 언어 분포 관측 |
| 멀티 sprint 자동 진행 워크플로 | 사용자 입력 불가·게이트 무력화 | — |

## 5. 축소 판단 트리거

각 마일스톤에서 아래 신호가 나오면 **즉시 범위를 줄인다**. 붙잡고 있다가 전체 일정을 망치지 않는다.

| M | 신호 | 축소 |
|---|---|---|
| M1 | 템플릿 검증 오탐 다수 | 필수 섹션을 줄이고 경고로 강등 |
| M2 | resync 가 불안정 | 수동 복구 절차 문서화로 대체 |
| M3 | 계층 정확도 <70% | 자동 판정 포기, `/tene:layers edit` 수동 확정만 |
| M3 | 특정 언어 팩 실패 | 그 언어는 Tier 3 전용 선언 |
| M4 | 갭 판정 오탐 다수 | 갭을 "후보"로 격하, 사람 확인 필수 |
| M5 | 브라우저 자동화 불안정 | UX 레이어를 수동 체크포인트로 |
| M6 | R1 연결 추론 오탐 | R1 을 "후보 제시 + 사람 확인"으로 |
| M8 | Eval 비용 과다 | 정직성 5종만 CI, 나머지 릴리즈 전 수동 |

### 축소해도 지켜야 하는 4가지

```
1. 4계층 + 6질문 절차       ← 기술부채 방어의 본체
2. blocking AC 게이트        ← spec driven 강제의 본체
3. insufficient 정직 표기    ← 신뢰의 본체
4. 시크릿 경계 (fail-closed) ← 안전의 본체
```

이 넷 중 하나라도 포기하면 제품의 정체성이 사라진다. **차라리 기능을 줄인다.**

## 6. 사람이 정해야 하는 정책

기본값을 제공하되 사용자가 확정한다. 미확정 시 **안전한 기본값을 적용하고 report R6 에 기록**한다.

| 항목 | 안전 기본값 | 사용자 결정 지점 |
|---|---|---|
| Profile | `standard` | `/tene:sprint init --profile` |
| 자동 진행 상한 | `design` 까지 | `--auto-until <phase>` |
| loop-check 반복 상한 | 3회 | `userConfig.max_loop_checks` |
| 문서 루트 | `docs/sprints/` | `userConfig.docs_root` |
| 문서 언어 | 세션 언어 감지 | 첫 sprint 에서 확정 후 고정 |
| 증거 보존 기간 | 무제한(수동 정리) | `/tene:clear` |
| 브라우저 자동화 계정 | 사용 안 함 | 사용자가 명시 |
| production 환경 실행 | **금지** | 명시 허용 필요 |
| non-blocking debt 이월 상한 | 3 sprint | `userConfig` |
| 워크플로 전환 임계 | AC 8개 | `userConfig.workflow_threshold` |
